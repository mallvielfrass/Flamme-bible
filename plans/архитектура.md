# Архитектура синхронизатора

Контракт на 9 ноября 2026. Проектор не делаем. Кода сервера и клиента ещё нет. Источники: `мое_представление.txt` и решения после него. Старые планы лежат в `old/` и этот контракт не заменяют.

Продукт — свой сервер и программа синхронизации для существующей VisioBible. Песни переносятся между компьютерами через аккаунт. Независимые добавления сохраняются. Сайт — регистрация, пространство, приглашение и состояние синхронизации.

Стек: сервер на Go, PostgreSQL, сайт на Vue 3 и Pinia. Первый клиент — CLI на Go. Оболочка со сканером папки VisioBible делается следом. Tauri не используется. Badger допустим позже только как хранилище текстов частей по хешу. Журнал синхронизации, пользователи и ревизии остаются в PostgreSQL.

## Что уже проверено

VBM: заголовок `VisioBibleModule`, версия `0x0102`, zlib, строки UTF-16LE. `$ID$` — номер для человека. `$FBID$` один раз пережил смену заголовка в VisioBible 2.3 под Wine: 51 песня, 292 части, 0 групп. Round-trip одного неизменённого файла был побайтно равен. Сохранение VisioBible само меняет LF/CRLF и конечные переводы строк частей. Группы в проверенных файлах пустые, файл с группами клиент не перезаписывает.

Модуль `visioBible/VisioBible2.5.0_1332_PE/Modules/rst+/`. После открытия и закрытия Библии в `bibleqt.ini` остались `BibleId` в шапке и `BookHash` у Бытия. Программа перезаписала `visiobible.cache` и `visiobible.idx`, ini и HTML не трогала. Это одна сборка, один модуль и одна книга. На остальные книги ключ пока не ставится.

План `Plans/plan.vplt` — XML `VisioBibleJournal`. Текстовый слайд: `Caption`, `Reference`, `Quote`, `Class="-1"`. `PlanDef.ini` держит журналы `Bible`, `Text`, `Songs`. История стихов и куплетов — в `History.ini`. При сохранении плана VisioBible пересобирает XML и стирает незнакомые теги.

## Пространства и сборники

`Dimension` бывает `personal` или `community`. Личное создаётся вместе с пользователем и выбрано по умолчанию. У общины есть имя, адрес, почта, конфессия и описание. Регистрация на сайте открытая. Пока нет SMTP, подтверждение почты не блокирует вход. В общину входят по одноразовой ссылке-приглашению. Роли `admin` и `member`. Оба правят песни. Admin приглашает и исключает. Исключение отзывает доступ, локальная очередь исключённого не удаляется.

Граница журнала — пространство. Пользователь берётся из сессии. Поле владельца в теле запроса игнорируется.

Песенник — корень или патч одного родителя. Участники общины правят общий сборник общины напрямую. Личный патч пишется поверх чужого родительского сборника и тело родителя не меняет. Сайт показывает один сборник и раздел добавленных. VisioBible патчей не понимает: клиент собирает один VBM.

Сборник, на который ссылаются патчи, скрывается, а не уничтожается. Публикация каталога в первый срез не входит, флаги публичности можно хранить заранее.

`$FBID$` — идентификатор песни. Хеш части и MinHash ищут совпадения и общее содержимое. Песня, отличающаяся словом, остаётся другой песней. Похожая песня у родителя не удаляет песню патча: скрытие копии делает человек.

## Данные и журнал

- `users`, `dimensions`, `memberships`, устройства, сессии.
- `songbooks`: fbid книги, названия, издатель, дата ревизии, комментарий, шаблон заголовка VBM, `parent_id`.
- `songs`: fbid, поля песни, сырой `properties`, ревизия, признак удаления.
- `song_order`: упорядоченный список fbid и ревизия. `$ID$` в этот список не входит.
- `sync_counters(dimension_id)`, неизменяемый `change_log`, идемпотентность `(dimension_id, device_id, operation_id)`, копии конфликтов.

Сессии непрозрачные, в базе только digest. Пароли Argon2id. TLS обязателен. JWT нет.

Порядок событий: `SELECT … FOR UPDATE` по счётчику пространства до выдачи seq. `BIGSERIAL` вне этой блокировки не используется. Конфликт seq не двигает. Повтор той же операции с тем же телом возвращает прежний результат. Другое тело с тем же id отклоняется. Курсор клиент двигает только вместе с применением страницы. `cursor` старше сохранённого журнала требует повторной загрузки снимка. Несинхронизированные локальные правки при этом остаются отдельной ветвью.

## Сборка VBM

Локальный VBM — снимок. Источник — родитель плюс патч выбранного пространства.

Порядок по умолчанию: fbid родителя, затем fbid патча, которых в родителе нет. Перестановка хранится полным списком fbid только у патча. Новая песня родителя, которой нет в пользовательском списке, добавляется в конец и показывается в dry-run. `$ID$` выставляется из позиции итогового списка при сборке. Строки родителя пачкой не перенумеровываются.

Собранный файл заменяет исходный модуль по тому же пути. Перед заменой сохраняются копии VBM и соседнего VBI. VisioBible закрыта. Новый файл разбирается заново. Проверка не прошла — на место возвращается копия. Привязка хранит фактический путь: VisioBible уже переводила имя файла в нижний регистр. `visiobible.idx` и `visiobible.cache` по сети не синхронизируются.

Настройки клиента на Windows — `AppData/flammebible`. Несколько установок или пустой результат требуют выбора папки. В поиск входят `C:\ProgramData\VisioBible Vx.x\Modules`, папка `Modules` рядом с программой и список из ini, если он есть.

## Правки одной песни

Первая успешная запись становится серверной ревизией. Второй при слиянии видит предупреждение у себя. Оба текста лежат, пока он не выберет.

1. В локальный модуль сначала попадает серверная версия. Человек сам правит её и отправляет новую ревизию поверх этой базы.
2. Его текст сохраняется новой песней с новым `$FBID$`. Серверная песня остаётся.

Автосклейки строк нет. Удаление против правки этим выбором молча не стирается: оба варианта остаются до явного ответа.

## Удаление автора и цепочка патчей

Удаление автора — tombstone в том сборнике, где песню удалили. В дочерние патчи оно не копируется. Патч хранит только своё решение: `suppress` или `retain` с последним текстом.

Ребёнок песню не менял — в собранном VBM её нет, вопрос не задаётся. Есть правка или песня стоит в его порядке — один вопрос: оставить или принять удаление. Ответ записывается один раз. Несколько детей решают отдельно.

Цепочка собирается от корня. Потомок видит уже решённый сборник родителя. У сборника один `parent_id`. Глубина не больше 8. `parent_id` на себя или на потомка отклоняется. Если цикл уже в данных, VBM не перезаписывается.

Родитель вернул песню, а `retain` хранит тот же текст — метка снимается. Текст разошёлся — это обычная правка патча поверх родителя.

## Тексты и планы

В первый срез не входят.

Идентификатор плана лежит в соседнем `имя.vplt.sync`: UUID плана и список пунктов из UUID и хеша известных полей. Хеш считается по полям, которые VisioBible сохраняет сама. Хеш файла только показывает, что файл менялся.

Имя и путь — локальная привязка. Тот же план на другом компьютере узнаётся по скопированному `.sync`. Файл без `.sync` — новый план, пока человек сам не свяжет его. Потерянный `.sync` не восстанавливается по похожим пунктам.

Тот же хеш на том же месте — тот же пункт. Тот же хеш на другом месте — смена порядка. Одинаковые хеши различаются позицией. Пропавший хеш и один новый на его месте — правка этого пункта. Неоднозначная замена помечает старый пункт удалённым и выдаёт новым новые UUID. `History.ini` получает свой `.sync` только если историю начнут синхронизировать отдельно.
